# ทำไม `analyze-proposal` ตอบ `ai_provider_error` "โมเดลจบลำดับอย่างผิดปกติ"

Imagine คุณสั่งโมเดลให้เขียนงานยาว ๆ แล้วมันวางกลางทางโดยไม่บอกว่าเสร็จหรือถูกตัด — ระบบของเราไม่รู้จะตีความยังไง เลยรายงานว่า "โมเดลจบลำดับอย่างผิดปกติ" นี่คือ error code `ai_provider_error` ที่คุณเห็นจาก `POST /ai/analyze-proposal`

## ระบบตัดสินว่า "ผิดปกติ" ยังไง

โมเดลทุกครั้งที่ตอบจบ จะส่ง "เหตุผลการจบ" (finish reason) มาด้วย บอกว่าจบเพราะอะไร เช่น `stop` = ตอบจบเองตามปกติ, `tool_calls` = ขอเรียก tool ก่อน, `length` = คำตอบยาวเกิน ceiling เลยถูกตัด ระบบของเรายอมรับแค่สามอันนี้ (`open-router-client.ts:226-229`) — อย่างอื่นที่เหลือทั้งหมดถูกยุบเป็น `"error"` ตัวเดียว แล้ว loop ฝั่งเรา (`react-loop.ts:96-102`) เห็น `"error"` ก็โยน `ai_provider_error` พร้อมข้อความนั้น

## อะไรทำให้ finish reason ตกไปอยู่กลุ่ม "อื่น" — 3 ทาง

1. **ผู้ให้บริการต้นทางล้มกลางทาง** — OpenRouter ส่ง `finish_reason: "error"` กลับมาตรง ๆ เช่น Google (เจ้าของโมเดล) หลุด/crash/โหลดแรงเกิน
2. **โดน safety filter ตัด** — OpenRouter ส่ง `finish_reason: "content_filter"` มา ตอนนี้ระบบแยกเป็น code ของตัวเองแล้ว: `ai_content_filtered` (message "โมเดลตัดคำตอบด้วย safety filter ของผู้ให้บริการ — retry ด้วยคำถามเดิมไม่ช่วย ต้องปรับเนื้อหาที่ให้โมเดลอ่าน", `retryable: false` — เกิดจากเนื้อหา input ไม่ใช่ความผิดพลาดชั่วคราว)
3. **Stream จบโดยไม่เคยมี finish reason เลย** — มี 3 สถานการณ์ย่อย: ได้ `[DONE]` เร็วเกินกว่าจะเห็น finish chunk, connection ถูกปิดสะอาดกลางทาง, หรือทุก chunk ที่ได้มามี `choices: []` (โค้ดเห็นแบบนี้แล้วข้ามเฉย ๆ) — ค่าเริ่มต้นของตัวแปรคือ `"error"` อยู่แล้ว (`open-router-client.ts:145`, `react-loop.ts:71`) เลยตกเป็น error โดยไม่มีใคร "สั่ง"

## ทำไม `usage` เป็น 0 ทุกช่อง และมันบอกอะไร

error event นี้จะใส่ `usage` มาแค่เมื่อระบบได้ตัวเลขจาก provider จริง (`react-loop.ts:124`) — ที่เห็น 0 ครบทุกช่องแปลว่า provider **ส่งตัวเลขมาจริง แต่รายงานเป็นศูนย์** คือ request ตายก่อนโมเดลจะประมวลผลอะไรเลย นี่คือหลักฐานว่าโอกาสสูงสุดคือทางที่ 1 (provider ปฏิเสธงานตั้งแต่ต้น) ผลข้างเคียงที่ดี: เนื่องจากโควตาคิดจาก token ที่ใช้จริง ครั้งนี้จึงไม่โดนหักโควตา

## เคสที่ "ไม่ใช่" อันนี้ (จำแนกด้วยรูป event)

| ถ้าเจอแบบนี้ | code ที่ได้ | ต่างจากเคสของเรายังไง |
|---|---|---|
| error chunk ที่ provider ยิงกลาง stream (HTTP ยัง 200) | `ai_stream_error` | นี่คือ provider บอกว่าผิดพลาดอย่างชัดเจน ไม่ใช่เดาจาก finish reason |
| HTTP ตอบ fail ก่อน stream เริ่ม (เช่น 429, key หมด) | `ai_rate_limited` ฯลฯ ผ่าน `wireError` | ยังไม่ได้เริ่ม generation เลย |
| fetch ไป OpenRouter ไม่ถึง / timeout | `ai_network_error` | ปัญหาอยู่ที่เครือข่ายฝั่งเรา |
| ปิด connection ทิ้งกลางทาง | `ai_aborted` | ใครบางคนยกเลิกเอง |
| คำตอบยาวเกิน ceiling ถูกตัด | `ai_invalid_request` ข้อความ "โมเดลตัดคำตอบยาวเกิน limit" | เป็น `length` ซึ่งอยู่ในกลุ่มที่ระบบยอมรับ จะแยกออกมาเป็นอีกข้อความ |

## ผลข้างเคียงเฉพาะ `analyze-proposal`

endpoint นี้ mint แผน (DMP) ใหม่ให้ก่อนรัน — ถ้า run ล้ม แผนที่เพิ่งสร้างถูกลบทิ้งทันที (`src/features/ai/README.md:48`) จึงไม่มีแผนว่างค้าง และไฟล์ proposal ยังไม่ถูกผูกกับโครงการ (ต้องรอ run สำเร็จ)

## จะทำยังไง

- **ยิงซ้ำ** — error นี้ `retryable: true` ใช้ `Idempotency-Key` **ใหม่** ในการ retry (key เก่าจะ replay ผลล้มเหลวเดิม 24 ชม.) และไม่เสียโควตาเพราะ usage เป็น 0
- **เจอซ้ำบ่อย → เปลี่ยนโมเดล** — ตอนนี้ `config.toml` ตั้ง `ai.models.analyze_proposal = "google/gemini-2.5-flash"` Gemini ผ่าน OpenRouter มีชื่อเรื่อง provider ล่มชั่วคราวและ safety filter ตัดง่าย (ตรงกับทาง 1 และ 2 ด้านบน) — ลอง slug อื่นที่รองรับ tool calling ดู
- **เห็น `ai_content_filtered`** — ไม่ใช่ความผิดพลาดชั่วคราว ยิงซ้ำด้วย input เดิมไม่ช่วย ต้องปรับเนื้อหาที่ให้โมเดลอ่าน (เช่น ส่วนของ proposal ที่ filter ติด) หรือเปลี่ยนโมเดลที่ filter หลวมกว่า
