DMP คืออะไร และมันคุมทั้งระบบนี้ไว้อย่างไร

เริ่มจากคำถามง่าย ๆ: งานวิจัยเกิดข้อมูลเยอะมาก แล้วใครจะดูแลมัน?

เวลาคนทำงานวิจัย จะมี "ข้อมูล" เกิดขึ้นตลอด — ไฟล์วัดผล, ภาพถ่าย, แบบสอบถาม, ตัวเลขในสเปรดชีต คำถามที่หน่วยงาน (มหาวิทยาลัย สถาบันวิจัย) อยากรู้คือ ข้อมูลพวกนี้จะเก็บไว้ที่ไหน ใครใช้ได้บ้าง แบ่งปันกับคนอื่นอย่างไร และหลังจบงานจะเก็บไว้ให้คนอ่านต่อหรือไม่?

DMP ย่อมาจาก Data Management Plan — แผนการจัดการข้อมูลวิจัย เป็นเอกสารที่นักวิจัยเขียนไว้ก่อนเริ่มงาน ตอบคำถามพวกนั้นทั้งหมดล่วงหน้า ลองนึกว่ามันคือ พิธีกรรมก่อนขึ้นบ้าน (แบบแปลนบ้าน) — ก่อนก่อสร้างจริง ต้องเขียนแบบแปลนว่าบ้านจะมีกี่ห้อง ท่อน้ำวิ่งยังไง ใครอนุมัติแบบแปลนนี้ แล้วค่อยลงมือสร้างตามแบบนั้น

สรุปสั้น ๆ: proposal บอกว่า "งานวิจัยนี้ทำอะไร" ส่วน DMP บอกว่า "ข้อมูลที่เกิดจากงานวิจัยนี้จะถูกจัดการอย่างไร" — ระบบในเอกสาร sequence diagrams ทั้งตัวคือเครื่องมือเขียน ส่งตรวจ และทำตามแผนนี้

ในระบบนี้ DMP ไม่ใช่ไฟล์เดียว แต่เป็นสามชั้นที่ซ้อนกัน

ถ้าอ่านไฟล์ sequence-diagrams.md จะเจอคำว่า DMP, DMP_VERSION, version in force สลับกันไปมา จริง ๆ มันคือสามชั้นของสิ่งเดียวกัน:

ชั้นคืออะไรเทียบกับบ้าน
DMPแผนทั้งหมดของโครงการหนึ่งงาน มีสถานะ draft / pending / approvedโครงการสร้างบ้านทั้งโครงการ
working draftฉบับที่นักวิจัยกำลังแก้อยู่ ยังไม่มีผลใด ๆกระดาษร่างที่สถาปนิกขีดเขียนอยู่
DMP_VERSIONภาพถ่าย (snapshot) ของแผน ณ วันที่ส่ง ถูกตรึงแล้ว แก้ย้อนไม่ได้แบบแปลนที่ประทับตราแล้ว
version in forceเวอร์ชันล่าสุดที่ถูกอนุมัติ — ฉบับที่ "มีผลจริง"แบบแปลนฉบับที่ใช้ก่อสร้างอยู่จริง
ทำไมต้องแยก draft กับ version? เพราะแผนเป็นข้อตกลง การเปลี่ยนข้อตกลงต้องผ่านคนตัดสิน ส่วนการร่าง ๆ แก้ ๆ ไม่ควรต้องรบกวนใคร — สองอย่างนี้จึงต้องอยู่คนละช่อง

ชีวิตของ DMP หนึ่งผืน ไล่ตาม flow ในเอกสาร

เอกสาร sequence diagrams เรียง 14 flow ตามลำดับ แต่ถ้ามองเป็นชีวิตของ DMP ตัวเดียว มันคือเส้นทางนี้:

แล้ว "DMP มีผลต่อเอกสารนี้อย่างไร?" — ตอบตรง ๆ คือ: มันคือทุกอย่าง

ถ้าถอด DMP ออกจาก sequence diagrams จะไม่เหลืออะไรเลย เพราะทุก flow ในเอกสารคือการกระทำ "กับ DMP" หรือ "เพราะ DMP" ดูได้จากสี่บทบาทนี้:

1. DMP เป็นเวทีที่ทุกตัวละครยืนอยู่

  • นักวิจัย (R) — เขียน draft, submit, ทำ tasks ที่แผนสั่ง
  • กรรมการ (C) — ตัดสินเวอร์ชัน pending ของ DMP (approve หรือส่งกลับ)
  • AI — อ่าน proposal แล้ว "เสนอ" เนื้อหาให้เติมใน draft (flow 3)
  • Backend/DB — เก็บ DMP, ตรวจกฎ, จดทุกการตัดสิน

2. DMP กำหนดว่า "การแก้แบบไหนต้องขออนุมัติ"

นี่คือหัวใจของ requirement หมวด 4.3 ที่ flow 8–9 ตีความออกมา ไม่ใช่ทุกการแก้มีค่าเท่ากัน:

ประเภทการแก้ตัวอย่างฟิลด์ผลในระบบ
แก้เล็ก (minor)contributor, cost, รายละเอียดไม่กระทบใครรูดลง version in force ทันที ไม่มีเวอร์ชันใหม่ ไม่รอใคร (flow 8)
แก้ใหญ่ (major)วันเริ่ม/สิ้นสุด, ethics, Indigenous, การเข้าถึงข้อมูลส่วนบุคคล, เพิ่ม/ลบ outputสร้าง DMP_VERSION ใหม่ เข้า pending รอกรรมการ (flow 9)
กฎสำคัญจากการตัดสิน 18 ตุลาคม 2026: กรรมการไม่ต้องอนุมัติครบทุกคน — reviewer คนใดคนหนึ่งตัดสินได้ หนึ่งเวอร์ชันมี decision เดียว สิ่งนี้ต่างจาก flowchart เดิม และเป็นเหตุผลที่ flow 6 เขียนว่า decided_by คนเดียว

3. DMP ที่ "มีผล" เป็นแม่พิมพ์ของ tasks

แผนที่ยัง draft ไม่ทำให้เกิดงานอะไรเลย ทันทีที่เวอร์ชันแรกถูกอนุมัติ (หรือ independent สรุปเองใน flow 7) ระบบจะแตกแผนออกเป็น tasks ชุดแรกโดยอัตโนมัติ (flow 12) นั่นแปลว่า DMP ไม่ใช่แค่เอกสารให้เซ็น แต่เป็น รายการสั่งงานที่มีชีวิต — ลบ output ออกจากแผนเมื่อไร tasks ของ output นั้นถูก cancel ตามไปด้วย (flow 11)

4. DMP คือสิ่งที่ export ออกไปให้คนนอกเห็น

flow 14 export เป็นมาตรฐานสากล (GCWG-RDA maDMP v3.0 หรือ RDA Common Standard v1.3) — สิ่งที่ออกไปคือ projection จาก version in force ไม่ใช่ฉบับร่างที่กำลังแก้อยู่ และถ้าเป็นแผน independent export จะเขียนช่องอนุมัติว่า "not applicable" เพราะไม่ผ่านกรรมการตั้งแต่แรก

ในฐานข้อมูล: แผนหนึ่งผืนเขียนลงอะไรบ้าง ในแต่ละช่วงชีวิต

ถ้าแงะดูใต้ฝา (จาก ERD ใน project-erd.md) แผนหนึ่งผืนไม่ได้เป็นแถวเดียวเงียบ ๆ แต่เป็น แถว DMP หนึ่งแถวที่เปลี่ยนตลอดเวลา + แถว DMP_VERSION ที่งอกทีละใบทุกครั้งที่ส่ง + แถว TASK ที่ผุดขึ้นเมื่อแผนมีผล และที่น่าประหลาดใจคือ datasets, contributors, costs ทั้งหลาย ไม่ใช่ตารางแยก — มันซ่อนอยู่ในช่อง draft เป็น JSON แนบข้างใน DMP แถวเดียวกันเลย

อ่านตารางนี้แล้วรู้เลยว่า "flow ไหน จิ้มตารางไหน"

ช่วงชีวิต (flow)สิ่งที่ถูกเขียนลงฐานข้อมูล
ร่างแก้ (flow 4)เขียนทับช่อง draft ของ DMP แถวเดียวเท่านั้น — ยังไม่แตะ DMP_VERSION เลย
Submit (flow 5)สร้าง DMP_VERSION ใหม่ (snapshot + changes + status=pending) · DMP.status = pending · plan_mode ถูกตรึงลงตัว DMP ครั้งแรกและครั้งเดียว
Approve (flow 6) / Self-finalize (flow 7)บนเวอร์ชัน: status=approved, decided_at, decided_by, approver (ภาพถ่ายตัวตนผู้อนุมัติ ณ วันนั้น) · DMP.status = approved, active_version = n, tasks_generated = true · เกิดแถว TASK ชุดแรก + NOTIFICATION
Minor edit (flow 8)รูดเข้า snapshot ของ version in force ตรง ๆ + จดใน minor_edits ของใบนั้น — ไม่มีแถวใหม่เกิดขึ้นเลย
Major revision (flow 9)DMP_VERSION ใบใหม่มี based_on (ตอนอนุมัติ ย้อนดูเทียบกับ based_on เพื่อดูด fix ที่รออยู่ → จด carried_minor_edits หรือ dropped_minor_edits) · เวอร์ชันถูกส่งกลับเขียน note บนตัวเอง
Archive (flow 13)DMP.archived_at = วันที่ — แค่ซ่อนจากหน้าจอ ทุกช่องข้างในคงเดิมทั้งหมด
Export (flow 14)ไม่เขียนอะไรเลย — export เป็น projection อ่านจาก snapshot ของ version in force แล้วคำนวณสด ไม่มีตารางเก็บ
ทำไม DATASET / CONTRIBUTOR / COST ถึงไม่ใช่ตารางแยก? เพราะมันเป็น "เนื้อหาของแผน" ที่มีชีวิตตามแผนเสมอ — วาดเป็นตารางแยกจะต้องตามซิงก์กับ snapshot เวอร์ชันทุกใบซึ่งยุ่งยาก เก็บเป็น JSON ใน draft และใน snapshot ของแต่ละเวอร์ชัน ทำให้ภาพถ่ายแต่ละใบสมบูรณ์ในตัวเอง ไม่ต้องประกอบกลับจากหลายตาราง
กฎเหล็กของฐานข้อมูลระบบนี้: ไม่มีปุ่มลบ — แผนถูก archive ไม่ใช่ลบ, task ที่มีงานบันทึกไว้ถูก cancel (จดสถานะเดิมไว้ใน cancelled_from) ไม่ใช่ลบ, โครงการที่ยังมีแผนอยู่ลบไม่ได้ เหตุผลคือทุกอย่างที่บันทึกการทำงานจริงคือหลักฐาน ฐานข้อมูลจึงถูกออกแบบให้ "จดทับได้ แต่ลบไม่ได้"

สรุป: จำสามประโยคนี้พอ

  1. DMP = แผนจัดการข้อมูลวิจัย คือข้อตกลงว่าข้อมูลของงานวิจัยจะถูกจัดการอย่างไร เขียนเป็น draft ก่อนเสมอ
  2. เฉพาะเวอร์ชันที่ถูกอนุมัติ (version in force) เท่านั้นที่มีผลจริง — มันกำเนิด tasks ถูก export และถูกอ้างอิง ส่วน draft คือกระดาษทด
  3. การแก้ไขถูกจำแนก minor/major จากเนื้อหาที่แตะ — minor รูดเข้าฉบับมีผลได้เลย major ต้องเวอร์ชันใหม่ + กรรมการคนใดคนหนึ่งตัดสิน
เหมือนแบบแปลนบ้านอีกครั้ง: ร่างกี่รอบก็แค่ร่าง แบบที่ประทับตราฉบับล่าสุดเท่านั้นที่ใช้ก่อสร้าง ถ้าจะขยายห้องน้ำ (แก้เล็ก) แจ้งรอบรู้ก็พอ แต่ถ้าจะเพิ่มชั้น (แก้ใหญ่) ต้องเสนอแบบใหม่ให้เซ็นใหม่ — ทั้งเอกสาร sequence diagrams 14 flow คือกลไกจัดการสามประโยคนี้ให้ครบทุกทาง
