ระบบ DMP คืออะไร?

อธิบายง่าย ๆ ทีละขั้นตอน จาก sequence diagrams ทั้ง 14 flows

เริ่มจากคำถามตรง ๆ — DMP คืออะไร

DMP ย่อมาจาก Data Management Plan หรือ "แผนการจัดการข้อมูลวิจัย" ฟังดูเป็นศัพท์เทคนิค แต่แท้จริงแล้วมันคือเอกสารที่ตอบคำถามง่าย ๆ เกี่ยวกับข้อมูลในงานวิจัยชิ้นหนึ่ง:

  • งานวิจัยนี้จะเก็บข้อมูลอะไรบ้าง?
  • ข้อมูลจะเก็บไว้ที่ไหน ใครเข้าถึงได้บ้าง?
  • จบงานแล้วจะแบ่งปันข้อมูลให้คนอื่นใช้ต่ออย่างไร?
  • มีเรื่องจริยธรรมหรือข้อมูลส่วนบุคคลที่ต้องระวังไหม?

ลองนึกว่างานวิจัยเป็นเหมือนการเดินทาง ข้อมูลก็คือสัมภาระ DMP ก็คือ "แผนการจัดการสัมภาระ" ที่เขียนไว้ล่วงหน้าว่าจะแพ็คอะไร เก็บไว้ตรงไหน และจะเอาออกมาแบ่งกันใช้ยังไงตอนถึงที่หมาย

ทำไมต้องมีแผนแบบนี้?

เพราะเมื่องานวิจัยเสร็จไปแล้ว ถ้าไม่มีใครรู้ว่าข้อมูลอยู่ไหน เข้าถึงยังไง ข้อมูลนั้นก็เหมือนหายไปเลย — เงินทุนวิจัยที่จ่ายไปก็เท่ากับเสียเปล่าครึ่งหนึ่ง มหาวิทยาลัยและหน่วยงานทุนจึงให้เขียนแผนนี้ก่อนเริ่มงาน

ระบบนี้ (backend ตัวนี้) ทำอะไรให้เรา

ระบบนี้คือ "โรงงานผลิตและอนุมัติแผน DMP" ที่พานักวิจัยไปตั้งแต่ต้นจนจบ ในหนึ่งรอบชีวิตของแผน มันทำ 4 อย่างใหญ่ ๆ:

  1. ช่วยเขียน — ให้ AI อ่าน proposal แล้วเสนอร่างแผนให้ นักวิจัยแก้ต่อได้ทั้งหมด
  2. จัดการการอนุมัติ — ส่งแผนให้กรรมการตรวจ ตีกลับกลับมาแก้ ส่งใหม่ จนอนุมัติ
  3. เปลี่ยนแผนเป็นงานจริง — พอแผนอนุมัติ ระบบแตกแผนออกเป็น task ที่ทำได้ทีละอย่าง พร้อม checklist และหลักฐาน
  4. เก็บทุกเวอร์ชันไว้หมด — แก้ครั้งไหน ใครอนุมัติ ตอนไหน ย้อนดูได้หมด และ export ออกมาเป็นไฟล์มาตรฐานสากลได้

ถัดจากนี้เดินทีละขั้นตอนตามเอกสาร 14 flows โดยแบ่งเป็น 4 กลุ่มเหมือนต้นฉบับ

กลุ่ม A — เริ่มต้น: บัญชีและโครงการ

1. Sign-up / Sign-in — เปิดบัญชีเข้าใช้งาน

นักวิจัยสมัครเองได้ โดยกรอก username, email และรหัสผ่าน ระบบจะตรวจว่า username กับ email ไม่ซ้ำกับใคร ถ้าซ้ำจะปฏิเสธแล้วบอกด้วยว่าซ้ำที่ช่องไหน ถ้าผ่านหมด รหัสผ่านจะไม่ถูกเก็บเป็นข้อความตรง ๆ แต่ถูก "หมัก" ด้วยวิธีเข้ารหัสแบบ bcrypt/argon2id เก็บเป็น hash — แม้แต่คนดูแลระบบก็อ่านรหัสผ่านจริงไม่ได้

ตอน sign-in ระบบเทียบ hash แล้วออก token ให้ และทุกอย่างที่ทำต่อจากนี้จะถูกจดว่า "ใคร" เป็นคนทำเสมอ

2. สร้างโครงการ + อัปโหลด proposal

โครงการวิจัยหนึ่งงาน = PROJECT หนึ่งอันในระบบ นักวิจัยตั้งชื่อ ใส่คำอธิบาย แล้วอัปโหลด proposal (ไฟล์ .docx) ของงาน

จุดสำคัญมีสองอย่าง:

  • โหมดของแผน (plan_mode) — ถ้านักวิจัยเป็นบุคลากรมหาวิทยาลัย (institutional) แผนจะต้องผ่านกรรมการ ถ้าเป็นประชาชนทั่วไป (independent) จะสรุปแผนเองได้ โหมดนี้ตั้งค่าเริ่มต้นตามประเภทบัญชีของคนสร้างโครงการ
  • proposal ตัวเดิมไม่หาย — ถ้าเอา proposal ใหม่มาแทน ไฟล์เก่าไม่ถูกลบ แค่ถูกจดว่า "ถูกแทนแล้ว" (superseded) และมีการแจ้งเตือนคนเกี่ยวข้อง

กลุ่ม B — การเขียนแผน

3. AI สร้างแผนจาก proposal

แทนที่นักวิจัยจะนั่งเขียนแผนจากศูนย์ ระบบให้ AI ช่วยเป็นผู้ช่วยร่างแผน เลือกได้หลาย action เช่น "อ่าน proposal ให้เข้าใจก่อน" "ร่างฟิลด์นี้ใหม่" "ร่างชุด task ให้หน่อย"

วิธีที่มันทำงาน (อ่านจาก diagram แล้วเข้าใจง่าย ๆ):

  • AI เป็นบริการภายนอก (OpenRouter) ระบบเรียกด้วย key ของระบบเอง ไม่ใช่ผู้ใช้
  • AI ทำงานเป็นวงจร — มันจะ "ขอดูข้อมูล" จากระบบ (อ่าน proposal, อ่านร่างปัจจุบัน, อ่าน metadata ของสาขา) แล้วค่อย ๆ ตอบ ไม่ได้เดาลอย ๆ และไม่มีสิทธิ์เขียนทับแผนเอง
  • ตอบกลับแบบ stream — เห็นข้อความไหลออกมาทีละชิ้นเหมือนคนพิมพ์อยู่
  • มี โควตา token รายคน — ก่อนเริ่ม run เช็กว่างบพอไหม ถ้าไม่พอปฏิเสธตั้งแต่ต้น ถ้า run กลางทางล้นโควตาก็ปล่อยจบ run นั้นก่อนแล้วค่อยนับเต็ม
  • ทุกอย่างที่ AI เสนอเป็นแค่ "ข้อเสนอ" — นักวิจัยแก้ได้ทุกจุดก่อนกดบันทึกลงร่างจริง

เทียบให้เห็นภาพ

AI ในระบบนี้เหมือน "ผู้ช่วยร่างเอกสาร" ที่มีห้องสมุดให้เปิดได้ แต่ไม่มีปากกา — มันบอกได้ว่าควรเขียนว่าอะไร แต่คนที่ลงนามลงในกระดาษคือนักวิจัยเสมอ

4. แก้ไข draft + validation

นี่คือวงจร "แก้ → บันทึก → แก้ต่อ" ที่ทำซ้ำได้จนพอใจ ระบบไม่ได้รับทุกอย่างเงียบ ๆ แต่ตรวจกฎทุกครั้ง เช่น:

  • วันสิ้นสุดต้องไม่มาก่อนวันเริ่มต้น
  • บอกว่ามีประเด็นจริยธรรม ต้องอธิบายด้วยว่าคืออะไร
  • ผู้ติดต่อ (contact) ต้องมีพอดีหนึ่งคน และต้องมี email
  • แผนที่เปิดให้คนภายนอกใช้ข้อมูล (open) ต้องระบุ license

ถ้าไม่ผ่าน ระบบปฏิเสธพร้อมระบุชื่อฟิลด์ที่ผิด — ผู้ใช้คลิกเข้าไปแก้จุดนั้นได้เลย ไม่ต้องไล่หาเอง ณ จุดนี้แผนยังเป็นแค่ "ร่าง" ยังไม่ผูกกับเวอร์ชันใด ๆ

กลุ่ม C — การส่งและการตัดสิน

5. Submit ครั้งแรก (institutional)

พอนักวิจัยกดส่ง มีเรื่องเกิดขึ้นหลายอย่างพร้อมกัน:

  1. ระบบตรวจ validation ซ้ำอีกรอบ (กฎชุดเดิมในขั้น 4)
  2. ปักหมุด plan_mode — โหมดของโครงการ ณ วินาทีที่ส่ง ถูกแช่ไว้กับแผนนี้ตลอดไป ต่อให้เปลี่ยนโหมดที่โครงการทีหลัง แผนที่ส่งแล้วก็ไม่ขยับ
  3. สร้างเวอร์ชัน 1 — สำเนาเต็มของแผน ณ ตอนส่ง ถูกแช่ไว้ สถานะ = รอตรวจ (pending)
  4. แจ้งเตือนทุกฝ่าย — นักวิจัยเห็นว่าส่งแล้ว กรรมการทุกคนเห็นว่ามีของรอตรวจ

ตอนนี้แผน ยังไม่มีผล ในทางระบบ — ต้องรออนุมัติก่อน

6. กรรมการตัดสิน: approve / ส่งกลับ

กรรมการเปิดดูเวอร์ชันที่รอตรวจ (เห็นทั้งสำเนาเต็มและจุดที่เปลี่ยน) แล้วเลือกทางใดทางหนึ่ง:

ตัดสินเกิดอะไรขึ้น
อนุมัติ (approve) ชื่อคนตัดสิน + เวลา ถูกจดลงบนเวอร์ชันนั้น แผนมีผลทันที และถ้าเป็นการอนุมัติครั้งแรก ระบบจะแตกแผนเป็นชุด task แรกให้อัตโนมัติ
ส่งกลับ (return) กรรมการเขียนเหตุผลไว้ ร่างที่นักวิจัยกำลังแก้อยู่คงเดิมทั้งหมด — แก้ต่อแล้วส่งใหม่ได้ทันที และเลขเวอร์ชันที่ถูกตีกลับจะไม่ถูกใช้ซ้ำอีก

จุดที่ต่างจาก flowchart เดิม — ตาม requirement

flowchart เก่าเขียนว่า "กรรมการอนุมัติครบทุกคน" แต่ requirement กำหนดว่า หนึ่งเวอร์ชัน มีการตัดสินได้ครั้งเดียว โดยคนเดียว — กรรมการคนใดคนหนึ่งตัดสินได้เลย คนอื่นแค่ได้รับแจ้ง

7. Self-finalize (independent)

สำหรับแผนโหมด independent (ประชาชนทั่วไป) ไม่มีกรรมการ — นักวิจัยกด "สรุปแผนเอง" ระบบตรวจ validation, สร้างเวอร์ชันที่สถานะ = อนุมัติทันทีโดยผู้ใช้เป็นคนตัดสินเอง, แตก task แรกให้ และแผนมีผลทันที ตอน export ออกไป ช่องการอนุมัติจะเขียนว่า "not applicable" — เพราะแผนประเภทนี้ไม่ต้องมีผู้อนุมัติตั้งแต่แรก

กลุ่ม D — หลังแผนมีผลแล้ว

พอแผนอนุมัติแล้ว คำถามต่อมาคือ "แก้ไขได้ไหม?" ได้ แต่ระบบแยกการแก้เป็นสองน้ำหนัก:

8. Minor edit — แก้เล็ก ไม่ต้องขออนุมัติ

การแก้ที่ไม่กระทบแก่นของแผน เช่น เพิ่ม/แก้ชื่อผู้ร่วมวิจัย (contributor), แก้ตัวเลขงบประมาณ (cost) — ระบบ diff ร่างกับสำเนาเวอร์ชันที่มีผลอยู่ เห็นว่าแตะแต่ฟิลด์ minor ก็ รวมเข้าเวอร์ชันเดิมเลย ไม่สร้างเวอร์ชันใหม่ ไม่รอใครอนุมัติ แค่จดบันทึกไว้ว่าใครแก้อะไรตอนไหน

9. Submit revision (major) — แก้ใหญ่ ต้องขออนุมัติใหม่

ฟิลด์พวกวันเริ่ม-วันจบงาน, เรื่องจริยธรรม, เรื่องข้อมูลส่วนบุคคล, การเพิ่มหรือลบผลลัพธ์วิจัย (output) — แตะฟิลด์เดียวก็นับว่าทั้งชุดเป็น major ต้องสร้างเวอร์ชันใหม่และขอตรวจใหม่

กติกาที่น่าสนใจจาก diagram นี้:

  • รอได้ทีละเวอร์ชัน — ถ้ามีเวอร์ชันค้างรอตัดสินอยู่ ส่งรอบใหม่ไม่ได้ ต้องรอตัดสินก่อน
  • ระหว่างรอ ยังแก้ minor ได้ — fix เล็ก ๆ ยังรวมเข้าเวอร์ชันที่มีผลอยู่ได้ตามปกติ
  • ตอนอนุมัติ ระบบ "เก็บงาน" ให้ — fix เล็ก ๆ ที่นักวิจัยทำทับระหว่างรอ จะถูกพกติดไปกับเวอร์ชันใหม่ (carried) แต่ fix ที่ไปชนกับสิ่งที่ revision ลบทิ้ง จะถูกจดว่า "ตัดทิ้ง" (dropped) อย่างชัดเจน ไม่หายเงียบ ๆ

10. Restore เวอร์ชัน — มีไว้ทำไม?

นี่คือฟีเจอร์ "ย้อนเวลา" ของแผน เหมือน version history ใน Google Docs — เผื่อนักวิจัยแก้ไปหลายรอบแล้วรู้สึกว่า "ฉบับก่อนหน้านี่ดีกว่า" ก็เลือกเวอร์ชันเก่ามาเป็นจุดตั้งต้นของร่างที่กำลังทำงานอยู่ได้

แต่ระบบตั้งกติกาสำคัญไว้ว่า restore ไม่ใช่การย้อนเวลา แต่เป็น "การแก้ไขครั้งหนึ่ง" ที่เอาเนื้อหาเก่ามาใส่ใหม่ — ฟังดูวน ๆ แต่มันสมเหตุสมผล: ถ้าเนื้อหาฉบับเก่าที่ดึงกลับมา ต่างจากฉบับที่มีผลอยู่ในจุด major (เช่น ลบ output ออกไปตอนหลัง) การ restore ก็คือการแก้ major ครั้งหนึ่ง ซึ่งต้องผ่านกรรมการเหมือนการแก้ทุกครั้ง ทำแบบนี้เพื่อกันใช้ restore ลัดประตูอนุมัติ — ย้อนกลับไปสู่เวอร์ชันที่มีของที่เคยถูกสั่งให้แก้ โดยไม่ขออนุมัติใหม่ ไม่ได้

สรุป 3 ทางที่ diagram วางไว้:

เวอร์ชันที่เลือก restoreระบบทำอะไร
เวอร์ชันที่ยังรอกรรมการตัดสินปฏิเสธทันที — ของที่รอตัดสินห้ามแตะ
เวอร์ชันที่มีผลอยู่ตอนนี้แค่เอาสำเนาของมันกลับเข้าร่างทำงาน (ทิ้งการแก้ที่ยังไม่ได้ส่ง) — อะไรที่มีผลอยู่ไม่เปลี่ยน ไม่จดอะไร
เวอร์ชันเก่าอื่น ๆ (อนุมัติก่อนหน้า / ถูกตีกลับ)โหลดเข้าร่างทำงาน จดว่า restore มาจากเวอร์ชันไหน แล้วเทียบกับฉบับที่มีผล — ต่างแค่ minor ก็รวมได้เลย, ต่างจุด major ต้อง submit ขออนุมัติใหม่

ข้อดีของการออกแบบแบบนี้

restore ช่วยให้ "การทดลองแก้ไปคนละทาง" ไม่มีวันทำระบบพัง — ลองแก้ไปเยอะ ๆ แล้วไม่ชอบ ก็ดึงฉบับที่ชอบกลับมาเริ่มใหม่ได้เสมอ แต่ความน่าเชื่อถือของฉบับที่มีผล (ที่กรรมการเคยอนุมัติ) ไม่ถูกลัดคอ เพราะทางกลับที่กระทบแก่นแผนยังต้องผ่านอนุมัติเหมือนเดิม

11. ลบ / นำกลับ research output

การลบผลลัพธ์วิจัย (เช่น ชุดข้อมูล) ออกจากแผนที่มีผลแล้ว ไม่ใช่การลบทันที — มันเป็น major edit จึงเป็นเพียง "ข้อเสนอ" ในร่างก่อน ต้องรอเวอร์ชันใหม่อนุมัติถึงจะมีผล ระหว่างรอนั้น output ยังนับว่าอยู่ งาน (task) ที่ผูกกับมันยังทำต่อได้

พอเวอร์ชันที่ลบ output อนุมัติแล้ว:

  • task ที่ผูกกับ output นั้นถูก cancel ไม่ใช่ลบ — จดว่ายกเลิกจากสถานะอะไร เพราะอะไร (output_removed) และจดชื่อ output ไว้ให้ตามเจอทีหลัง
  • ถ้าวันหนึ่งนักวิจัยเอา output ตัวเดิมกลับมาในเวอร์ชันใหม่ (ผ่านการอนุมัติ) ระบบจะเสนอให้เปิด task คืนทีละตัว — ไม่เปิดเองอัตโนมัติ เพราะการ cancel ครั้งนั้นผ่านการอนุมัติมาแล้ว การเปิดคืนจึงควรเป็นทางเลือกของคน ส่วน task ที่ยกเลิกด้วยมือเองไม่ถูกเสนอให้เปิดคืน

12. ทำงาน tasks — แผนที่อนุมัติแล้วกลายเป็นงานจริง

task คือหัวใจของ "แผนที่มีชีวิต" — แผนไม่ใช่เอกสารที่เขียนแล้วจำศีลในตู้ แต่แตกออกเป็นงานที่ต้องทำ เช่น "ทำเอกสารอธิบายชุดข้อมูล" "เก็บไฟล์เข้าคลัง" โดย:

  • เปอร์เซ็นต์ความคืบหน้า คำนวณจาก checklist จริง ไม่ใช่ตัวเลขที่ใครตั้งเองได้ — ทำไปเท่าไรคือเท่านั้น
  • แนบหลักฐานได้ทั้งไฟล์และลิงก์/DOI
  • งานที่บันทึกความคืบหน้าแล้ว ลบไม่ได้ — ที่มี evidence, ติก checklist ไปแล้ว หรือปิดงานไปแล้ว ยกเลิกไม่ได้ (เพราะจะทับบันทึกจริง) ทำได้แค่เปิดกลับ ส่วน task ที่ยังไม่มีใครเริ่ม ยกเลิกหรือลบก็ได้

หลักคิดเบื้องหลัง

ทุกอย่างที่คือ "การบันทึกการทำงานจริง" ของนักวิจัย ระบบจะไม่ทำลาย — ลบได้แค่ของที่ยังไม่มีความหมายในทางประวัติศาสตร์ของโครงการ

13. Archive แผน / ลบโครงการ

ระบบนี้ไม่มีทางลบแผนเลย — แผนที่ไม่อยากเห็นแล้วเก็บเข้า archive ได้ (แค่ซ่อนจากหน้าลิสต์ ยังค้นเจอผ่าน filter และ unarchive กลับมาได้ครบทุกอย่าง) และโครงการจะลบได้ก็ต่อเมื่อไม่มีแผนอยู่เลยแม้แต่แผนที่ archive แล้ว — กันการลบพลาดทั้งประวัติงานวิจัย

14. Export มาตรฐาน — ส่งมอบแผนให้โลกภายนอก

แผนที่มีผลอยู่ export ออกมาได้เป็นไฟล์ตามมาตรฐานสากล (maDMP v3.0 หรือ RDA Common Standard v1.3) เพื่อส่งให้หน่วยงานทุนหรือหน่วยงานกำกับใช้ได้จริง

สำคัญคือ export เป็น "การฉายภาพ" (projection) จาก เวอร์ชันที่มีผล เสมอ ไม่ใช่จากร่างที่กำลังแก้ค้างอยู่ — สิ่งที่ยังไม่อนุมัติจะไม่ปรากฏในไฟล์ที่ส่งออก และระบบจะบอกบนหน้าจอด้วยว่ามีการแก้ที่ยังไม่โชว์ใน export นี้ ก่อนอนุมัติครั้งแรก export ได้จากร่าง แต่สถานะจะบอกตรง ๆ ว่า "ยังไม่ส่ง" หรือ "รอตรวจอยู่"

สรุป — ทั้งหมดนี้ให้ประโยชน์อะไร

  • นักวิจัย ได้ผู้ช่วย AI ร่างแผน, ได้ checklist งานที่ตามได้ว่าทำถึงไหน, และมั่นใจว่าแก้ผิดย้อนกลับได้เสมอ (restore)
  • กรรมการ / สถาบัน ได้ความมั่นใจว่าทุกการแก้ที่กระทบแก่นแผนต้องผ่านตาคนก่อนมีผล และทุกการตัดสินมีชื่อ เวลา เหตุผล จดไว้ครบ
  • โลกภายนอก ได้แผนที่ export เป็นมาตรฐานสากลได้ทันที พร้อมสถานะการอนุมัติที่ตรวจสอบได้

แก่นคิดที่ร้อยทั้ง 14 flows เข้าด้วยกันมีสองข้อ: หนึ่ง — ทุกอย่างสำคัญต้องผ่าน "เวอร์ชัน + การตัดสิน" ไม่มีการเปลี่ยนของที่มีผลอยู่แบบเงียบ ๆ สอง — ไม่มีอะไรถูกลบเลือน มีแต่ถูกจด ไม่ว่าจะเป็น minor edit, dropped fix, cancelled task หรือ superseded proposal
